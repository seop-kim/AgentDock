# 중단된 실행 정리 — 범위 정의서

- 작성일: 2026-10-02
- 출처: `agents/HANDOVER.md` 5장 "다음에 할 일" 5번 — "서버가 죽으면 `PENDING`/`RUNNING`/`WAITING_CHILD` 로 남아 화면이 '실행 중'으로 계속 보이고 폴링도 계속 돈다."
- 상태: **결정 대기** — 아래 갈림길은 사용자 확인 전까지 구현하지 않는다.

## 1. 배경 (코드 확인 결과)

- `ExecutionStatus` 는 `PENDING/RUNNING/WAITING_CHILD/WAITING_INPUT/SUCCEEDED/FAILED/CANCELLED` 7종이다. HANDOVER 작성 시점(2026-10-01)에는 `WAITING_INPUT` 이 없었지만, 이후 ask 계약 기능이 들어오면서 추가됐고 `ExecutionService.isRunning(status)`(private, L201)가 이미 `PENDING/RUNNING/WAITING_CHILD/WAITING_INPUT` 4종을 "아직 안 끝남"으로 묶어 워크트리 삭제 409 가드에 쓰고 있다. 즉 서버 재기동 시 고아로 남는 상태는 **3종이 아니라 4종**이다.
- 기존 `POST /executions/{id}/cancel`(`ExecutionController` L47-50 → `ExecutionService.cancel` L325-333)은 **OS 프로세스만 죽인다**(`ProcessService.cancel`, in-memory `Map<String, Process>` 조회). DB `execution.status` 를 `CANCELLED` 로 바꾸는 코드가 없다. 서버가 죽은 뒤에는 이 맵도 비어 있어 **지금의 cancel API는 재기동 후 멈춘 실행에는 효과가 없다** — 수동 취소를 쓰려면 상태 전이 로직을 함께 추가해야 한다(기존 버그, 이번 범위에 포함할지 결정 필요 → 2장 D).
- `Task.status`(`CREATED/IN_PROGRESS/SUCCEEDED/FAILED`)는 루트 실행이 끝났을 때 `ExecutionService.publishFinished` → `ExecutionFinishedEvent` 로만 갱신된다. 실행을 강제로 끝내도 이 이벤트를 발행하지 않으면 Task 는 계속 `IN_PROGRESS` 로 남아 화면이 "실행 중"으로 보이는 증상이 그대로 남는다.
- 워크트리/브랜치 자동 삭제는 설계상 없다(HANDOVER 7장) — 이번 정리는 **DB 상태 전이만** 다루고 워크트리 정리는 기존 `DELETE /executions/{id}/worktree` 로 사람이 한다. 범위 밖.
- 취소 전파(부모 취소 시 자식도 취소, HANDOVER 5장 6번)는 **별도 미해결 항목**이다. 이번 작업과 겹치는 지점(트리 전체 정리 시 자식도 같이 처리할지)은 있지만, "살아있는 실행의 취소 전파" 자체는 이번 범위가 아니다.

## 2. 결정이 필요한 갈림길

### A. 적용 방식 — 자동 정리 / 수동 취소 / 둘 다

| 옵션 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A1. 자동 정리만 | 서버 기동 시 고아 상태 실행을 일괄 정리 | 구현 범위 작음, 사람 개입 불필요 | 서버가 살아 있는 동안 CLI 가 죽거나 멈춘 개별 실행은 못 잡음(수동 취소 API 자체의 버그도 남음) |
| A2. 수동 취소만 | 화면에 취소 버튼 노출 + cancel API 상태 전이 버그 수정 | 서버가 멀쩍이 살아 있어도 그때그때 대응 가능 | 서버 재기동 직후 쌓인 고아 실행을 매번 사람이 눌러서 지워야 함 |
| **A3. 둘 다 (추천)** | 기동 시 자동 정리 + 화면 수동 취소 둘 다 구현 | 재기동 직후는 자동으로, 평소 멈춘 실행은 수동으로 — 두 경로가 겹치지 않고 서로 보완 | 범위·구현량이 A1/A2 합보다 커짐 |

**추천: A3.** 자동 정리는 "서버가 죽었다가 다시 뜬 경우"만 잡고, 수동 취소는 "서버는 살아 있지만 특정 실행이 멈춘 경우"(CLI 프로세스 행, 무한 대기 등)를 잡는다 — 겹치는 문제가 아니라 서로 다른 문제라서 하나만 고르면 다른 쪽 증상이 남는다.

### B. 자동 정리 시 상태 전이 — `CANCELLED` vs `FAILED`

| 옵션 | 내용 |
| --- | --- |
| B1. `CANCELLED` | "사람/시스템이 끝까지 돌리지 않고 멈췄다"는 중립적 의미. 실행 자체의 성패를 판단하지 않는다. |
| B2. `FAILED` | "실패"로 표시. `errorMessage` 에 사유를 남기는 기존 `markEscalated` 패턴과 일관적이나, CLI/에이전트 오류로 보일 수 있어 원인(서버 재기동)과 다른 뜻으로 읽힌다. |

**추천: B1 (`CANCELLED`).** `errorMessage` 필드(기존에 있음, `markEscalated` 참고)에 "서버 재기동으로 중단됨" 같은 사유를 남겨 화면에 왜 끝났는지 보이게 한다. `FAILED` 는 실제 실행 실패(계약 파싱 실패, CLI 에러)에만 쓰는 게 기존 의미와 맞는다.

### C. 자동 정리 대상 상태 범위

| 옵션 | 내용 |
| --- | --- |
| C1. HANDOVER 원문 그대로 | `PENDING`/`RUNNING`/`WAITING_CHILD` 3종만 |
| **C2. (추천) 코드 기준 4종** | 위 3종 + `WAITING_INPUT` — 사람의 답을 기다리는 실행도 서버가 죽으면 답을 받을 프로세스가 없는 고아 상태다. |

**추천: C2.** HANDOVER 문서는 `WAITING_INPUT` 이 생기기 전에 쓰였다. `ExecutionService.isRunning` 이 이미 4종을 "안 끝남"으로 묶어 쓰고 있으므로, 정리 대상도 같은 기준을 따르는 게 일관적이다.

### D. 트리 범위 — 루트만 vs 트리 전체(자식 포함)

| 옵션 | 내용 |
| --- | --- |
| D1. 루트만 정리 | 트리의 루트 실행만 상태를 바꾼다 | 자식 실행은 그대로 고아 상태로 남아 `isRunning` 가드(워크트리 삭제 409 등)에 계속 걸림 |
| **D2. (추천) 트리 전체 정리** | 고아 상태인 실행을 루트/자식 구분 없이 전부 정리 | 부모-자식 취소 "전파" 로직(HANDOVER 5장 6번, 살아있는 실행 대상)을 새로 만들 필요 없음 — 이번엔 전부 이미 멈춘 상태이므로 일괄 업데이트로 충분 |

**추천: D2.** 자동 정리는 "살아있는 트리를 취소 전파"하는 게 아니라 "이미 멈춘 고아 행을 일괄 정리"하는 것이라 전파 로직 없이 `WHERE status IN (...)` 일괄 업데이트로 끝난다. 수동 취소(화면)에서 부모를 누르면 자식도 취소할지는 전파 이슈와 겹치므로 이번 범위에서는 **각 실행 행 단위로만** 취소 버튼을 노출한다(E 참고).

### E. 수동 취소 — 버튼을 노출할 상태 + 기존 cancel API 버그 처리

- 노출 상태: **C 에서 정한 4종(`PENDING`/`RUNNING`/`WAITING_CHILD`/`WAITING_INPUT`)** 전부에 취소 버튼을 둔다(이미 `isRunning` 기준과 동일). 종료 상태(`SUCCEEDED`/`FAILED`/`CANCELLED`)에는 버튼을 숨긴다.
- **기존 cancel API 버그**: 현재 `ExecutionService.cancel` 은 DB 상태를 바꾸지 않는다. 수동 취소를 실제로 쓰려면 "OS 프로세스 종료 + `execution.status = CANCELLED` 전이 + Task 상태 동기화(`publishFinished`, 루트인 경우)"를 같이 고쳐야 효과가 있다. **이 버그 수정을 이번 범위에 포함할지** 결정이 필요하다 — 포함하지 않으면 "화면에서 수동 취소 가능"이라는 목표 자체가 동작하지 않는다.

**추천: 포함한다.** 버튼만 추가하고 API 동작을 고치지 않으면 눌러도 화면이 바뀌지 않아 사용자가 더 혼란스럽다.

## 3. 완료 조건 (체크리스트)

A3(둘 다) + B1(`CANCELLED`) + C2(4종) + D2(트리 전체) + E(버그 수정 포함) 기준:

- [ ] 서버 기동 시 고아 상태(`PENDING`/`RUNNING`/`WAITING_CHILD`/`WAITING_INPUT`) 실행을 전부 조회해 `CANCELLED` 로 전이하고 `errorMessage` 에 사유(예: "서버 재기동으로 중단됨")를 남긴다.
- [ ] 위 전이 대상 중 **루트 실행**(`root_execution_id IS NULL`)이 있으면 해당 Task 를 `publishFinished` 와 동일한 경로로 갱신해 화면이 "진행중"으로 안 보이게 한다.
- [ ] `POST /executions/{id}/cancel` 이 OS 프로세스 종료뿐 아니라 `execution.status = CANCELLED` 전이와 (루트면) Task 상태 동기화까지 한다.
- [ ] 프론트엔드 실행 트리/실행 요약 카드에서 `PENDING`/`RUNNING`/`WAITING_CHILD`/`WAITING_INPUT` 상태인 실행에 취소 버튼을 노출하고, 누르면 위 API 를 호출해 화면이 즉시 `CANCELLED` 로 갱신된다.
- [ ] 자동 정리는 **기동 시 한 번만** 돌고 이후 주기적 폴링은 하지 않는다(상시 감시는 범위 밖).
- [ ] JUnit: 자동 정리(기동 시 4종 전이 + Task 동기화), cancel API 상태 전이, 완료/실패 상태는 건드리지 않는다는 것을 검증하는 테스트 추가.
- [ ] `npm run build --workspace=apps/frontend` 통과, 8081/3031 에서 실측(강제로 서버 종료 후 재기동 → 고아 실행이 `CANCELLED` 로 바뀌는지, 화면에서 취소 버튼으로 실행이 바뀌는지).
- [ ] `agents/HANDOVER.md` 5장 5번 항목을 "해결됨"으로 갱신(완료 커밋/검증 내용 반영).

## 4. 우선순위

1. 자동 정리(기동 시, B/C/D 결정 반영) — 서버 재기동마다 반복되는 증상이라 우선순위가 높다.
2. cancel API 버그 수정 + 화면 취소 버튼 — 자동 정리와 별개 경로지만 "화면에서 멈춘 실행 끝내기"가 바로 다음으로 필요하다.

## 5. 범위 밖 (이번에 하지 않음)

- 취소 **전파**(부모 취소 시 자식도 취소, HANDOVER 5장 6번) — 살아있는 실행을 대상으로 하는 별개 작업.
- 워크트리/브랜치 자동 삭제 — 기존 설계대로 사람이 `DELETE /executions/{id}/worktree` 로 한다.
- 상시 감시(주기적 폴링으로 멈춘 실행 감지) — 자동 정리는 기동 시 1회만.
- 세션 재개(`--resume`) 등 HANDOVER 5장의 다른 미해결 항목.

## 6. 사용자 확인 필요

위 A~E 는 추천안이 있지만 최종 선택은 사용자 몫이다. 특히:

- **A(적용 방식)**: 둘 다 할지, 하나만 할지.
- **E(기존 버그 수정 포함 여부)**: cancel API 상태 전이 버그를 이번에 같이 고칠지, 아니면 "화면 노출"만 하고 버그 수정은 별도 항목으로 분리할지.

나머지(B/C/D)는 코드 일관성 근거가 분명해 추천안으로 진행해도 무방하다고 판단하나, 역시 최종 결정은 사용자가 한다.
