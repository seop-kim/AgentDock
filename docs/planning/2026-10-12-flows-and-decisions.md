## 2. C — 변경사항 diff

**목적**: 실행 트리(루트)가 바꾼 파일 목록의 **파일별 unified diff** 를 창으로 본다. (계약: `2026-10-12-diff-schedules-merge-policy-contract.md` §1)

### 2.1 화면 흐름 단계

1. 사용자가 **실행목록 `/tasks`** 에서 행을 눌러 실행 트리 창(`ExecutionTreeModal`)을 연다(또는 프로젝트 상세의 채팅 실행 요약 카드 → 트리 창).
2. 트리 **루트 행**에 병합 상태 배지(병합됨/수동 병합 필요)와 함께 **변경 파일 목록**(`A path` 등)이 보인다(`TreeResultLine`). 변경 파일이 1개 이상일 때만 **"변경 diff 보기"** 버튼이 뜬다(변경 0건이면 버튼 없음).
3. 버튼을 누르면 `ExecutionDiffModal` 이 뜬다(기존 `modal`+`execution.module.css` 글래스 창 재사용, 새 창 아님).
4. 창 상단: `실행 #{id} · 트리가 바꾼 파일별 unified diff · 커밋 {resultCommit}`.
5. 왼쪽(또는 위) 파일 목록 + 본문: 파일을 고르면 그 파일의 diff 본문. 바이너리는 `binary` 배지, 잘렸으면 `truncated` 표시, 실패 파일은 `error` 한 줄. `additions`/`deletions` 배지.
6. **닫기** → 창만 닫힘. 트리 창·목록 상태는 변하지 않는다.

**상태 표현**: 서버 API 가 아직 없으면 창은 파일 대신 `"변경 diff API(GET /executions/{id}/diff)를 기다리는 중"` 문구를 그린다(현재 구현과 일치).

### 2.2 결정 지점

#### C-1. diff 창 진입 방식
- **배경**: 트리에서 diff 로 들어가는 입구를 어디에 둘지. 지금은 루트 행의 "변경 diff 보기" 버튼이다.
- **선택지 A**: 루트 행의 **버튼**으로 연다(변경 파일이 있을 때만 노출).
- **선택지 B**: 루트 행을 **클릭**하면 곧바로 diff 창을 연다(트리 창 위에 겹쳐).
- **영향**: A는 "트리 보기"와 "diff 보기"가 분리돼 실수로 창이 겹치지 않고, 변경 0건이면 버튼이 숨겨져 빈 창이 안 뜬다. B는 클릭 한 번이 줄지만, 행 클릭의 기존 의미(트리 상세)와 충돌하고 변경 0건에도 빈 창이 뜬다.
- **기본 제안**: **A**(현재 구현 유지). 계약 §1.8 도 "루트 행 → 파일 클릭 → diff 창"을 전제한다.

#### C-2. 표시 범위 — 파일 하나씩 vs 전체 한 번에
- **배경**: diff 본문을 언제 얼마나 가져오는가. 계약은 `?path=<repo상대경로>` 로 **파일 하나만** 받는 길과, 생략해 **전체**를 받는 길을 모두 둔다.
- **선택지 A**: **파일 하나씩**(`?path=`) — 목록은 `changed_files` 로 그리고, 파일을 고를 때만 그 파일 diff 를 읽는다(큰 트리 보호).
- **선택지 B**: 창을 열 때 **전체**를 한 번에 받아 클라이언트에서 파일 전환.
- **영향**: A는 첫 응답이 작고 큰 트리·거대 파일에서도 창이 빨리 뜨지만 파일 전환마다 요청이 난다(왕복 ↑, 각 요청 20초 상한). B는 한 번에 받아 전환이 즉각이지만 큰 트리에서는 첫 응답이 무겁고 `MAX_DIFF_CHARS` 절단이 여러 파일에 걸린다.
- **기본 제안**: **A(파일 하나씩)**. 계약 §1.8 이 "전체를 한 번에 받지 않는다 — 큰 트리 보호"로 못 박았다. 현재 `ExecutionDiffModal` 은 전체를 받는 형태이므로, 구현 시 이 결정에 맞춰 `?path=` 단위로 바꾼다.

#### C-3. 열어 둔 diff 창의 실시간 재조회 여부
- **배경**: 전역 이벤트가 `execution.changed` 를 보낼 때 열린 diff 창을 다시 읽을지.
- **선택지 A**: **다시 읽지 않는다** — 트리 결과(커밋·changed_files)는 한 번 확정되면 변하지 않는다(계약 §1.6).
- **선택지 B**: `execution.changed` 마다 다시 읽는다.
- **영향**: A는 불필요한 git 호출을 막는다(비싼 작업). B는 확정된 결과를 반복 계산해 서버 부하만 늘린다.
- **기본 제안**: **A**. 단, 데이터 담당(19)의 배선에는 "열어 둔 diff 창도 재조회"라는 문구가 있어 **불일치**다 — 구현 시 A 로 맞춘다(§9 정합성 경고).

## 3. D — 반복·예약 실행 (`/schedules`)

**목적**: 프로젝트 명령을 주기로 반복한다. 즉시 실행·예약 실행 모두 기존 `POST /projects/{id}/commands`(= `TaskService.command`)를 재사용한다. (계약: diff-schedules-merge-policy §2)

### 3.1 화면 흐름 단계

1. 사이드바 **예약**(`/schedules`, `CalendarIcon` + MENUS) 진입. 화면 마운트 시 `loadSchedules()`.
2. 목록: 각 행에 이름 · 주기 배지 · 켜짐/꺼짐 배지 · 프로젝트·대상(에이전트/팀/마스터) · `다음 {nextRunAt} · 지난 {lastRunAt} · 실행 #{lastExecutionId}`.
3. **새 예약**: 이름 · 프로젝트 셀렉트 · 주기 · (크론식이면 cron 입력) · 보낼 대상(마스터/에이전트/팀) · 지시(prompt) → 생성. 프로젝트 안 이름 중복은 409.
4. **즉시 실행**: `POST /schedules/{id}/run` → 서버가 `TaskService.command` 재사용 → `{taskId, rootExecutionId}` 반환. **회차(next_run_at)는 소모하지 않는다.**
5. **켜기/끄기**: `enabled` 토글 → 끄면 스케줄러가 건너뛴다(부분 인덱스 `WHERE enabled`).
6. 결과 관찰: 예약이 만든 실행은 **실행목록 `/tasks`·프로젝트 실행 트리**에 나타난다(예약 화면이 실행 상태를 이중 추적하지 않는다).
7. 스케줄러 tick(기본 30초)이 `next_run_at` 이 지난 켜진 예약을 일으키고, 트리거는 **workers 풀**에서 돌아 스케줄러 스레드를 막지 않는다.

**상태 표현**: API 가 없으면 목록·생성 자리는 대기 문구, 버튼은 비활성(현재 구현과 일치).

### 3.2 결정 지점

#### D-1. 주기 표현 방식
- **배경**: 사용자가 주기를 어떻게 입력하는가. 프론트 `Schedule` 타입은 `cadence`(HOURLY/DAILY/WEEKLY/CRON)를, 백엔드 계약은 `cron_expression`(Spring cron 6필드)+`timezone` 만 둔다 — **표현이 어긋난다**.
- **선택지 A**: **프리셋(cadence) + 고급 CRON** — 매시간/매일/매주는 UI 가 서버 cron 으로 변환하고, CRON 을 고르면 사용자가 6필드를 직접 넣는다.
- **선택지 B**: **CRON 문자열만** — 화면에도 cron 만 받는다.
- **영향**: A는 비전문 사용자가 쉽게 만들 수 있고(현재 화면이 A), 서버는 여전히 cron 하나만 저장한다. B는 화면이 단순하지만 매일 예약도 6필드를 익혀야 한다. A 로 가면 **cadence↔cron 변환은 프론트 책임**이 되고 서버 계약은 바뀌지 않는다.
- **기본 제안**: **A(프리셋 + CRON)**. 단 서버 계약(`cron_expression`)은 그대로 두고, `cadence` 는 **화면 전용 표시/입력**으로만 쓴다(저장은 cron). 스케줄 요청 본문(`ScheduleRequest`)에 `cadence` 를 넣지 않는다 — 넣으려면 계약을 함께 고친다(§9).

#### D-2. 놓친 실행 처리
- **배경**: 앱이 꺼져 있던 동안 지나간 회차를 어떻게 하는가. 계약은 `catch_up_policy`(SKIP/RUN_ONCE)로 확정했다.
- **선택지 A**: **기본 `SKIP`**(건너뛰고 다음 회차로 전진) — 놓친 회차는 `schedule_run(SKIPPED)` 한 줄만 남긴다.
- **선택지 B**: **기본 `RUN_ONCE`**(한 번만 따라잡음).
- **영향**: A는 폭주·중복 트리가 없다(앱이 오래 꺼져 있었어도 지금 한 번만). B는 "밀린 작업을 한 번은 돌린다"는 기대를 만족하지만, 예약이 밤사이 여러 번 걸리는 작업이면 원치 않는 실행이 생길 수 있다. 어떤 값이든 **RUN_ALL(전부 재생)은 없다**(계약 확정).
- **기본 제안**: **A(생성 기본 SKIP)**, 사용자가 예약별로 RUN_ONCE 로 바꿀 수 있게 한다.

#### D-3. 즉시 실행과 회차의 관계
- **배경**: "지금 한 번 실행"이 다음 예약 회차에 영향을 주는가.
- **선택지 A**: **영향 없음** — 즉시 실행은 회차를 소모하지 않는다(`next_run_at` 그대로).
- **선택지 B**: 즉시 실행이 다음 회차를 당긴다(실행했으니 다음 주기로 미룬다).
- **영향**: A는 "지금 테스트해 보고 정규 회차는 그대로"라는 직관과 맞다. B는 회차 계산이 상태(마지막 즉시 실행 시각)에 의존해 껐다 켜면 어긋나기 쉽다.
- **기본 제안**: **A**. 계약 §2.3 도 "수동 실행은 회차를 소모하지 않는다"로 확정.

#### D-4. 예약 실행 실패를 사람에게 알리는 길
- **배경**: 예약 트리거가 실패(에이전트 불가·CLI 실패)하거나 트리가 실패로 끝났을 때, 사람이 어떻게 아는가.
- **선택지 A**: **실행목록·트리에만 남기고 별도 알림 없음**(사용자가 목록에서 본다).
- **선택지 B**: **알림으로 흘린다** — H 알림에 새 이벤트 `SCHEDULE_FAILED` 를 추가해 규칙에 걸린 채널로 발송하고, 요청 인박스에도 띄운다.
- **영향**: A는 최소 구현이지만 무인 예약 실패를 아무도 모를 수 있다. B는 H 계약에 `NotificationEventType.SCHEDULE_FAILED` 를 **D·H 합의로 추가**해야 하고(현재 H 계약은 이 값을 넣지 않았다), 인박스 items 에 새 kind 를 더한다.
- **기본 제안**: **B(알림으로)** — 무인 실행이 목적이므로 실패를 조용히 두지 않는다. 단 `SCHEDULE_FAILED` 는 D·H 계약을 함께 고쳐 확정한 뒤 구현한다(§9).

## 4. E — 워크트리 자동 정리 · 병합 정책

**목적**: 트리(워크트리)가 끝난 뒤 **자동 병합·정리를 어디까지** 할지 전역 정책으로 정한다. (계약: diff-schedules-merge-policy §3, CONVENTIONS "워크트리 격리")

### 4.1 화면 흐름 단계

1. **설정 `/settings`** 진입 → `SECTIONS` 의 **병합 정책**(`MergeIcon`) 항목 → `MergePolicySettings`.
2. 토글 4개: 자동 병합 / 워크트리 자동 정리 / 브랜치 자동 삭제 / 깨끗할 때만 병합. 각 토글에 한 줄 설명(현재 구현과 일치).
3. **저장** → `PUT /settings/merge-policy`. 저장 시점 이후 끝나는 트리부터 적용(이미 도는 실행은 소급하지 않는다).
4. 실제 동작(트리 종료 훅, `ExecutionService.recordTreeResult` 자리): 메인 저장소가 깨끗하면 `git merge --no-ff` → `MERGED`; 아니면 `MANUAL`(사유+브랜치). 정책에 따라 워크트리/브랜치 정리.
5. **MANUAL** 이면 **요청 인박스**에 `수동 병합` 행이 뜬다(`RequestsPanel`, 이미 구현). 사용자가 변경을 정리한 뒤 **지금 병합**(`retryMerge`)을 누른다. 트리 창 루트 행에도 `다시 병합` 버튼이 있다.

### 4.2 결정 지점

#### E-1. 자동 병합 기본값
- **배경**: 새 프로젝트/미설정 상태에서 자동 병합을 켜 둘지.
- **선택지 A**: **기본 켜짐**(깨끗할 때만 병합 `requireCleanTarget=true` 와 함께) — 트리가 끝나면 사람 개입 없이 되돌린다.
- **선택지 B**: **기본 꺼짐** — 항상 MANUAL 로 두고 사람이 병합.
- **영향**: A는 무인 실행의 결과가 바로 메인에 반영된다(자동화 이득). B는 안전하지만 매번 사람이 병합해야 한다. CONVENTIONS 는 "깨끗할 때만 자동 병합"을 이미 규칙으로 두므로 A 가 그 규칙과 일관된다.
- **기본 제안**: **A**(`autoMerge=true`, `requireCleanTarget=true`, 프론트 `DEFAULT_POLICY` 와 일치).

#### E-2. 자동 정리 범위
- **배경**: 병합 후 무엇을 지우는가. 워크트리 폴더와 전용 브랜치는 서로 다른 대상이다.
- **선택지 A**: **워크트리 폴더까지 정리**(`autoCleanupWorktree=true`), **브랜치는 남긴다**(`autoCleanupBranch=false`).
- **선택지 B**: **워크트리 + 브랜치 모두 정리**.
- **영향**: A 는 병합 커밋이 조상으로 남아 브랜치를 지워도 복구 가능하나, 브랜치 이름(`agentdock/exec-*`)으로 추적하려면 A 가 낫다. B 는 디스크·브랜치를 깔끔히 하지만, 지운 뒤 추적은 커밋 sha 로만 가능하다. **C 의 diff** 는 메인 저장소가 git 객체를 공유하므로 브랜치가 지워져도 동작한다(계약 §1.4) — 즉 C 는 B 를 막지 않는다.
- **기본 제안**: **A**(워크트리만 정리, 브랜치 보존). 프론트 기본값(`autoCleanupWorktree=false`)보다 한 단계 적극적이지만, 정리 안 하면 워크트리 폴더가 무한히 쌓이므로 워크트리는 켜 둔다. 브랜치는 사용자가 명시적으로 켤 때만 지운다(되돌리기 어려움 — 확인 후).

#### E-3. MANUAL 처리 방식
- **배경**: 자동 병합이 막힌(`MANUAL`) 트리를 사람이 어떻게 처리하는가.
- **선택지 A**: **요청 인박스의 "지금 병합" 버튼**(`retryMerge`) 으로 처리(기존 경로 재사용).
- **선택지 B**: 사람이 저장소에서 **수동 git** 으로 병합(앱은 사유·브랜치만 알려 줌).
- **영향**: A 는 앱 안에서 끝나고, `retryMerge` 가 깨끗한지 다시 보고 병합을 시도한다(여전히 막히면 다시 MANUAL). B 는 앱 변경 없이 가능하지만 앱이 브랜치·상태를 계속 MANUAL 로 들고 있어 이력이 어긋날 수 있다.
- **기본 제안**: **A(인박스 버튼)** 를 기본으로, B 를 안내 문구로 병기("변경을 정리한 뒤 '지금 병합', 또는 브랜치를 직접 병합"). 이미 구현된 인박스를 그대로 쓴다.

## 5. G — 비용 · 예산

**목적**: 기간별 사용량(실측 계측값만)과 프로젝트 월 예산을 보고, 80%에서 경고한다. (계약: cost-budget-notification §3.1)

### 5.1 화면 흐름 단계

1. 사이드바 **비용·예산**(`/costs`, `CoinIcon` + MENUS) 진입. 화면 마운트 시 실행 목록(참고값)과 `loadCostUsage(from, to)`.
2. 기간 선택(최근 7/30/90일). 기간 변경 시 `GET /costs/usage?projectId=&from=&to=&bucket=` 재조회.
3. 합계 카드(총비용·토큰·실행 수) + 버킷(일/주/월) + 프로젝트별 표.
4. 프로젝트별 **예산 입력/해제** → `PUT/DELETE /projects/{id}/budget`. 미설정은 `GET .../budget` 404 → "예산 미설정"으로 표시.
5. 예산 대비 사용률과 `budget.level`(`OK`/`WARN`/`EXCEEDED`)로 색·문구 표시. 80% 도달 경고는 **별도 API 가 아니라** usage 응답의 `budget.level`/`percent` 로 그린다.
6. 서버는 주기 검사(`@Scheduled`)로 임계 도달 시 `notified_month` 를 남기고 `budget.changed` 를 발행(H 규칙이 있으면 `BUDGET_WARNING` 발송). 같은 달에 두 번 뜨지 않는다.

**상태 표현**: 집계 API 가 없으면 화면이 들고 있는 실행 목록의 실측값으로 **전체 기간 참고값**만 보여 주고(모의 아님, 현재 구현), 기간 집계·예산 설정은 대기 문구.

### 5.2 결정 지점

#### G-1. 예산 단위·기간
- **배경**: 예산을 어떤 주기로 거는가.
- **선택지 A**: **월 단위만**(프로젝트당 활성 1개, 계약의 `project_budget`).
- **선택지 B**: **월 + 총액(누적 상한)** 을 함께 둔다.
- **영향**: A는 회계가 단순하고 월 경계(UTC `date_trunc('month')`)가 명확하다. B는 "이 프로젝트에 총 얼마까지"를 표현할 수 있지만 기간 리셋 규칙이 늘어난다.
- **기본 제안**: **A(월 단위만)**. 계약 §G-1 이 월 단위·프로젝트당 1개로 확정. 총액이 필요해지면 추가 전용으로 확장.

#### G-2. 예산 초과 시 동작 (핵심 결정)
- **배경**: 지출이 예산을 넘었을 때 앱이 무엇을 하는가. 계약은 **경고만**으로 두고 차단/승인은 이 계약에 넣지 않았다(253 결정 뒤).
- **선택지 A**: **경고만**(`WARN`/`EXCEEDED` 표시 + 토스트/알림). 실행은 계속된다. 실행 차단·409 는 없다.
- **선택지 B**: **초과 시 실행 차단**(초과 프로젝트에서 새 실행을 409/403 으로 거부).
- **영향**: A는 관측·경고 도구로 남고 기존 실행 흐름을 건드리지 않는다(추가 전용). B는 `DelegationService.start`/`TaskService.command` 진입에 예산 가드를 넣어야 하고, 초과 상태가 된 트리의 자식 위임을 어디서 끊을지(트리 예산 `--max-budget-usd` 와의 관계)까지 정해야 하며, 이미 도는 실행의 처리도 정해야 한다 — 범위가 크고 실패 모드가 늘어난다.
- **기본 제안**: **A(경고만)**. 근거: 이 계약은 "80% 경고 발행"까지이고 차단은 별도 기획·계약이 필요하다. 차단이 필요하면 먼저 "누가/어디서 끊는가"를 이어서 결정한다.

#### G-3. 초과 시 승인 흐름
- **배경**: 초과 프로젝트에서 사람이 승인해야 실행하는 흐름을 둘지.
- **선택지 A**: **승인 흐름 없음**(이번 범위 밖).
- **선택지 B**: **초과 시 실행 전 승인 요청**(요청 인박스에 "예산 초과 — 실행 승인?" 항목을 띄우고, 승인하면 1회 허용).
- **영향**: A는 현재 계약대로 추가 작업이 없다. B는 G-2 의 B(차단)를 전제로 하고, 인박스 items 에 새 kind + 승인 API + 승인 기록이 필요하다 — 백엔드·프론트·계약이 함께 늘어난다.
- **기본 제안**: **A(승인 흐름 없음)**. G-2 를 A(경고만)로 두는 한 승인 흐름은 성립하지 않는다. 차단을 택하면 B 를 같은 계약에서 함께 확정한다.

#### G-4. 경고 표시 위치
- **배경**: 80% 경고를 어디에 띄우는가.
- **선택지 A**: **비용·예산 화면 안**에서만(합계 카드 + 프로젝트 행).
- **선택지 B**: 화면 안 + **전역 토스트**(전이 시 1회) + H 알림(`BUDGET_WARNING`).
- **영향**: A는 조용하지만 사용자가 `/costs` 를 열지 않으면 모른다. B는 실행 중에도 알 수 있으나 토스트 규칙(종류별 1회)과 중복되지 않게 `notified_month` 로 접어야 한다.
- **기본 제안**: **B**. 단 토스트는 `budget.changed` 로 `level` 이 `WARN`/`EXCEEDED` 로 **새로 진입할 때만** 1회(디자인 스펙 I4 토스트 규칙 준수). H 규칙이 없으면 토스트만.

## 6. H — 알림 채널

**목적**: 웹훅/Slack/메일 채널과 "어떤 사건을 어느 채널로" 규칙을 관리하고 테스트 발송한다. **비밀값은 DB 에 저장하지 않는다**(`secret_ref`=환경변수 이름). (계약: cost-budget-notification §3.2)

### 6.1 화면 흐름 단계

1. 알림 설정 화면(설정 안쪽 `SECTIONS` 또는 최상위 `/notifications` — §6.2 H-1 변형) 진입 → `loadNotifications()`.
2. **채널** 목록: 종류(WEBHOOK/SLACK/EMAIL)·이름·켜짐/꺼짐·`secretResolved`(설정됨/미설정). 생성/수정 시 종류별 `config`(EMAIL 은 host/port/from) + `secretRef`(환경변수 이름).
3. **테스트 발송**: `POST /notifications/channels/{id}/test` → 결과(성공/실패·HTTP 코드·사유)와 `notification_delivery` 기록. `secretRef` 환경변수가 없으면 409, 서버 egress 꺼짐이면 403.
4. **규칙** 목록: 채널 · 이벤트(`EXECUTION_SUCCEEDED`…`BUDGET_WARNING`) · 범위(전역/프로젝트) · 켜짐/꺼짐. 중복(채널·이벤트·범위)은 409.
5. 발송은 서비스 계층의 변화 지점(실행 종료·`WAITING_INPUT`·`MANUAL` 병합·`BUDGET_WARNING`)에서 `dispatch` → 규칙·채널을 골라 **workers 풀에서 비동기** 발송(요청·실행 스레드 비차단).
6. 채널·규칙 변경 시 `notification.changed` 발행 → 화면은 채널·규칙만 재조회.

**상태 표현**: API 가 없으면 채널·규칙 자리는 대기 문구, 버튼 비활성.

### 6.2 결정 지점

#### H-1. 알림 설정의 자리
- **배경**: 알림 설정을 어디에 두는가.
- **선택지 A**: **설정 `/settings` 안쪽 섹션**(`SECTIONS` 에 "알림" 추가, E 의 병합 정책과 같은 방식).
- **선택지 B**: **최상위 메뉴 `/notifications`**(사이드바 `BellIcon`).
- **영향**: A는 설정 항목이 한곳에 모여 일관되지만, 알림을 자주 보는 사용자에게는 깊다. B는 접근이 빠르지만 채널 CRUD·규칙·테스트가 붙어 사이드바 항목이 하나 늘어난다. 화면 담당(18)의 `프론트화면18.md` 는 `/notifications` 최상위 페이지를 가정하고, 디자인 스펙은 "설정 항목을 추가하려면 SECTIONS 에 추가"라 한다 — **어긋난다**.
- **기본 제안**: **A(설정 안쪽)** — 설정 화면 규칙(CONVENTIONS: 설정 항목은 SECTIONS 로 구분)을 따른다. 최상위 메뉴를 원하면 이 결정을 먼저 확정하고 화면 담당과 맞춘다(§9).

#### H-2. 규칙 우선순위 — 전역 vs 프로젝트
- **배경**: 같은 이벤트에 전역 규칙(NULL)과 프로젝트 규칙이 함께 걸릴 때.
- **선택지 A**: **둘 다 발송**(합집합) — `project_id IS NULL OR project_id = 이벤트 project` 인 enabled 규칙 전부.
- **선택지 B**: **프로젝트 규칙이 있으면 전역 규칙 무시**(프로젝트가 재정의).
- **영향**: A는 계약의 `dispatch` 선택식과 일치하고 "전역 기본 + 프로젝트 추가"가 자연스럽다(단, 같은 채널이 양쪽에 걸리면 두 번 발송될 수 있다). B는 프로젝트별로 전역을 끌 수 있지만, "이벤트×프로젝트에 프로젝트 규칙이 하나라도 있으면 전역 전체를 끈다"는 규칙이 직관과 어긋날 수 있다.
- **기본 제안**: **A(둘 다 발송)**. 계약 §3.2 의 `dispatch` 가 A 다. **중복 발송**은 화면에서 "같은 채널이 전역·프로젝트에 모두 걸려 있습니다" 경고로 안내한다(자동 차단하지 않는다).

#### H-3. 지원 채널 범위
- **배경**: v1 에서 어느 채널까지 지원하는가.
- **선택지 A**: **WEBHOOK · SLACK · EMAIL 3종**(EMAIL 은 `spring-boot-starter-mail` 신규 의존).
- **선택지 B**: **WEBHOOK · SLACK 2종**(메일은 다음 단계).
- **영향**: A는 계약의 3종(enum `NotificationChannelKind`)과 일치하고 메일 의존 1개가 늘어난다. B는 의존이 없지만 enum·마이그레이션(체크 제약)을 나중에 넓혀야 한다(추가 전용으로 가능하나 화면·검증도 손댐).
- **기본 제안**: **A(3종)**. 계약 §H-1 이 `kind IN ('WEBHOOK','SLACK','EMAIL')` 로 확정했고 프론트 타입도 3종이다. 다만 **EMAIL 발송은 `secret_ref`(SMTP 비밀번호) 환경변수가 없으면 409** 이므로, 환경변수 미설정 프로젝트는 테스트로 미리 확인하게 한다.

> 참고: **egress 403** — 서버 egress off(`agentdock.notifications.egress-enabled=false`)일 때 발송·테스트는 403. 이는 에이전트 `PermissionProfile` 과 엮지 않는다(계약 §3.3).

## 7. 프로젝트/조직 템플릿 복제 (소규모 · 계약 없음)

**목적**: 기존 프로젝트(또는 조직)의 구성을 새 프로젝트로 **복제**해 세팅 시간을 줄인다. **이 후보는 계약서가 아직 없다** — 아래는 흐름·결정 **제안**이며, 구현 전에 별도 계약(`...template-clone-contract.md` 류)으로 데이터 모델·API 를 확정해야 한다.

### 7.1 화면 흐름 단계 (제안)

1. **프로젝트 목록 `/projects`** 또는 **프로젝트 상세의 설정 창**(`ProjectSettingsModal`)의 `⋮`/메뉴에 **"템플릿으로 복제"** 를 둔다(새 화면을 만들지 않는다).
2. 복제 창(`ConfirmDialog` 확장 또는 작은 폼): **원본**(현재 프로젝트/다른 프로젝트) · **새 이름**(기본 "원본 이름 복사본") · **포함 항목 체크**(에이전트·그룹·프롬프트·워크스페이스 할당·예약·알림 규칙·병합 정책…) → **복제**.
3. 서버가 새 프로젝트를 만들고 선택 항목을 복사한다(에이전트·그룹은 새 id, 프롬프트 텍스트 복사, 워크스페이스 할당은 **경로만** 참조).
4. 완료 후 **새 프로젝트 상세**로 이동. `project.changed` 이벤트로 목록이 갱신된다.

### 7.2 결정 지점

#### T-1. 복제 단위
- **배경**: 무엇을 통째로 복제하는가.
- **선택지 A**: **프로젝트 단위** — 한 프로젝트의 에이전트·그룹·프롬프트·설정을 새 프로젝트로.
- **선택지 B**: **조직 단위** — 여러 프로젝트를 한 번에 새 조직/세트로.
- **영향**: A는 기존 도메인(project/agent/group)만 쓰고 화면도 프로젝트 목록 하나로 끝난다. B는 "조직"이라는 상위 개념·API·화면이 필요하며(현재 스키마에 조직이 없다), 워크스페이스·런타임 상태까지 어디까지 복사할지가 급격히 커진다.
- **기본 제안**: **A(프로젝트 단위)** 부터. 조직 복제는 프로젝트 복제가 안정된 뒤 별도 후보로 올린다.

#### T-2. 복제 포함 항목
- **배경**: 복사할 것과 복사하지 않을 것의 경계.
- **선택지 A**: **구성만 복사** — 에이전트(+persona·model·mode·permission)·그룹(+leader·prompt)·프로젝트 `masterAgent`/`masterPrompt`·워크스페이스 **할당**(경로 참조). **실행/로그/Task/예약 회차/발송 기록은 복사하지 않는다.**
- **선택지 B**: 위 + **예약·알림 규칙·병합 정책**도 복사.
- **영향**: A는 "빈 프로젝트를 같은 팀 구성으로 시작"이라는 핵심 가치를 빠르게 준다. B는 예약(`schedule`)·알림(`notification_rule`)이 프로젝트 FK 를 갖고 있어 **복사 시 중복 규칙 409·이름 중복**을 관리해야 하고, 병합 정책은 전역 설정이라 애초에 프로젝트별로 복사할 값이 없다(E 는 전역).
- **기본 제안**: **A(구성만)** 을 v1 로. 예약·알림 규칙 복사는 "이름/규칙 충돌 시 건너뜀" 규칙과 함께 다음 단계로. **자격증명/비밀값(`secret_ref`)은 절대 복사 대상에 넣지 않는다**(CONVENTIONS: 앱은 토큰/키를 저장하지 않는다) — 채널을 복사하더라도 `secret_ref`(환경변수 이름)만 옮기고 값은 옮기지 않는다.

#### T-3. 이름·충돌·되돌리기
- **배경**: 복제본의 이름과 실패 시 상태.
- **선택지 A**: **이름 자동 접미**("(복사본)") + **전부 성공 또는 전부 실패**(한 트랜잭션). 에이전트/그룹 이름은 프로젝트 안에서만 유일하므로 충돌 없음.
- **선택지 B**: 사용자가 새 이름을 강제 입력하고, **부분 성공**도 허용.
- **영향**: A는 결과가 예측 가능하고 실패 시 찌꺼기가 없다. B는 유연하지만 반쯤 복제된 프로젝트가 남아 사용자가 손으로 정리해야 한다.
- **기본 제안**: **A(접미 자동 + 원자적)**. 되돌리기 어려운 동작이므로 **확인 창**(대상=원본, 영향="새 프로젝트가 만들어집니다", 되돌리기=삭제로만 가능)을 쓴다 → 만든 뒤 되돌리려면 프로젝트 삭제(기존 위험 동작 규칙 그대로).

## 9. 정합성 경고 (계약·프론트 사이 어긋남 — 구현 전 확인)

1. **D-1 cadence vs cron**: 프론트 `Schedule` 타입의 `cadence`(HOURLY/DAILY/WEEKLY/CRON)는 백엔드 계약(`cron_expression`+`timezone`)에 없다. 기본 제안대로 **cadence 는 화면 전용**, 저장은 cron. `ScheduleRequest` 에 cadence 를 넣으려면 계약을 함께 고친다.
2. **C-2 / C-3**: 프론트 데이터 담당(`.agentdock/share/프론트데이터19.md`)과 화면의 `ExecutionDiffModal` 은 diff 를 **전체 한 번에** 받고 `execution.changed` 시 **재조회**하는 형태다. 계약 §1.6·§1.8 의 기본 제안(파일 하나씩·재조회 안 함)과 다르다 → 구현 시 계약에 맞춘다.
3. **G API 경로**: 프론트는 `/costs/usage`·`/costs/budgets` 를, 계약은 `GET /executions/usage`·`GET/PUT/DELETE /projects/{id}/budget` 을 확정했다. 기본 제안은 **계약 경로**다(클라이언트 경로만 맞추면 됨).
4. **H 화면 자리**: `프론트화면18.md` 는 `/notifications` 최상위 페이지를 가정하나 기본 제안은 **설정 안쪽**이다(디자인 스펙·CONVENTIONS 근거). 최상위로 갈 거면 화면 담당과 먼저 합의.
5. **D-4 `SCHEDULE_FAILED`**: H 계약 `NotificationEventType` 에 **아직 없다**(계약 §5 경고). D·H 계약을 함께 고쳐 확정한 뒤 구현한다.
6. **Flyway 번호**: C/D/E=V23~V25, G/H=V26~V28. 백엔드 API 지시(`prompts/247.md`)의 "V26" 중복 주의(`.agentdock/share/데이터설계담당.md` §1). 병합 전 대조.
7. **템플릿 복제**: 계약·API·화면 모두 **없다**. 이 문서는 흐름·결정 제안일 뿐이며, 구현 전 별도 계약서가 필요하다.
